== Fundamentals

Embedded software is built under constraints that are always present, even when
 they are not obvious at first.
The processor may be small, memory may be limited, timing may be strict, and
power may matter from the first prototype.
At the same time, the code must remain maintainable enough to grow into a real
product.

The problem space is therefore not just about writing code that works.
It is about balancing hardware limits, system behavior, and long-term
maintainability.
That is why this book starts with the fundamentals before moving into tools,
architecture, and communication.

=== Common constraints

.Common constraints in embedded projects.
[cols="1,5",options="header"]
|===
|Constraint|What it means
|Memory|Defines what can be stored, allocated, and buffered. It affects stack size, heap use, data structures, and how much code the system can carry.
|Timing|Defines when work can be done and how much jitter the system can tolerate. It affects interrupts, scheduling, and the order in which tasks must run.
|Power|Defines how often the processor can run, how long the system can stay awake, and how long batteries last. It affects sleep modes, duty cycle, and peripheral use.
|Reliability|Defines how the software reacts when signals fail, peripherals misbehave, or assumptions are violated. It affects error handling, timeouts, and recovery paths.
|===

These constraints are not independent.
A change that improves one area often affects another, so embedded software
requires trade-offs instead of isolated decisions.
