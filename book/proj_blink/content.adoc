=== LED blink

The first project in this book is the classic **blink** application. Although
simple, it is one of the most valuable exercises in embedded programming. A
successful blink verifies that the complete software and hardware chain is
working correctly: the project builds successfully, the firmware is flashed to
the target board, the microcontroller executes the program, and a GPIO pin is
able to control a physical device.

At first glance, blinking an LED may appear trivial, but it establishes the
foundation for every subsequent project in this book. Once GPIO control is
working, the same concepts can be extended to buttons, sensors, communication
interfaces, displays, and many other peripherals.

[IMPORTANT]
The overall program structure is identical across all supported boards, but the
onboard LED is **not** wired the same way on every board. Consequently, the
GPIO used to control the LED is board-specific.

A statement such as `gpio_put(25, 1)` may work perfectly on one board but have
no visible effect on another because the onboard LED is not always connected
directly to a GPIO pin on the main microcontroller.

For this reason, the examples in this section intentionally keep the program
structure unchanged while adapting only the board-specific LED configuration.
This highlights an important principle in embedded software: application logic
should remain portable, while hardware-specific details should be isolated
whenever possible.

The original Raspberry Pi Pico and the Raspberry Pi Pico 2 W provide a good
example of this hardware variation.

On the original Pico, the onboard LED is connected directly to a GPIO pin of
the microcontroller, allowing the firmware to control it by simply driving that
GPIO.

The Pico 2 W, however, introduces integrated Wi-Fi and Bluetooth hardware. To
support this design, the onboard LED is connected through the wireless chip
rather than directly to the RP2350 microcontroller. As a result, the LED is no
longer controlled by toggling a normal GPIO pin.

In particular, GPIO 25, which developers often associate with the onboard LED
on earlier Pico boards, is no longer available for that purpose on the Pico 2
W. Code that directly calls `gpio_put(25, 1)` will therefore not blink the
onboard LED. Instead, the Pico SDK provides the appropriate board-specific
definitions and APIs that abstract these hardware differences.

This is an excellent example of why embedded software should rely on the board
support package (BSP) or SDK whenever practical instead of hardcoding hardware
details. Doing so makes applications easier to port to new boards and reduces
the amount of code that must change when the underlying hardware evolves.

To play with this example you need the following files from
`../examples/blink_rp2040/` or `../examples/blink_rp2350/` folders:

* `blink_simple.c` - C source code
* `CMakeLists.txt` - Configuration file used by the CMake meta-build system
* `.microCI.yml` - Pipeline

Once you have these three files in a folder just execute:

[,shell]
----
microCI | bash
----

==== Loading firmware

===== If already in BOOTSEL mode

[source,console]
----
$ picotool load -x build/blink_simple.uf2
----

===== If your code is actively running

Force a quick reset and flash with the `-f` flag.

[source,console]
----
$ picotool load -fx build/blink_simple.uf2
----

[TIP]
**microCI** uses least privilege principle.

[IMPORTANT]
To deploy on hardware requires more privileges than the normal user supports by default.

The new options in `.microCI.yml` file are:

* `run_as: root` - execute commands in this step as `root`.
* `privileged: true` - the container gains almost full access to the host's kernel, hardware, and underlying system tools.
* `volumes:` - To map a Linux host's entire USB bus (`/dev/bus/usb`) to a Docker container
* `only: load` - Steps with `only` are executed alone and outside of the default pipeline
